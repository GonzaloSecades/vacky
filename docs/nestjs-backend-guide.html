Target and boundaries

Build one modular NestJS application with PostgreSQL. Keep the Next.js frontend at the repository root during migration. Use a separate worker process from the same backend codebase when durable jobs become necessary. Keep UploadThing and Google integrations until their replacement paths pass verification.

Destination, place/activity, and itinerary recommendations share this backend. Live collaboration is not planned. AI model calls and recommendation algorithms are outside the first backend parity milestone. Microservices, Kubernetes, event sourcing, a graph database, and automatic vector storage are deferred.

Keep controllers thin. Services own use cases and transactions. Keep database access inside the owning module or a focused database provider. Do not create generic repositories, abstract base services, or empty modules for hypothetical features.

Working defaults

These are proposed implementation defaults. Confirm them in Step 1 before installing packages.

  • REST under /api/v1, with OpenAPI as the external contract.
  • PostgreSQL with Prisma for typed persistence and versioned migrations.
  • Opaque, server-stored sessions with HTTP-only cookies and Argon2id password hashes.
  • One bounded database pool per process. Account for API replicas and workers in its connection budget.
  • Runtime DTO validation. Reject unexpected fields and invalid enum, date, coordinate, and length values.
  • DTOs are Zod 4 schemas. One schema supplies runtime validation, z.infer types, and the OpenAPI schema through @nestjs/swagger.
  • Parse every response through its response schema so unknown fields, such as hashes, are stripped at runtime.
  • Explicit response DTOs. Never expose persistence models, password hashes, or token hashes.
  • Structured logs, request IDs, health checks, and graceful shutdown from the first running slice.
  • PostgreSQL integration tests plus HTTP tests for auth, ownership, and transactions.
  • Redis with BullMQ when the first persistent background job is implemented.

Choose an HTTP adapter supported by the pinned Nest version and required middleware. Current Nest documentation recommends NodeAdapter from v12.3. Confirm compatibility before adopting it. Fastify remains an alternative when a required integration needs its plugin system. Do not choose an adapter from a hello-world benchmark alone.

Frontend and backend both run Node 24.22.3. The frontend moved from 22.20.0 on 2026-11-19 and passed lint and build. Pin exact Node, Nest, CLI, Prisma, and PostgreSQL versions. Do not run latest generators without checking their requirements.
